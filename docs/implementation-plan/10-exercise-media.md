# Exercise and muscle media

## MVP decision

Image uploads are not part of the MVP. Muscle and exercise creation/editing
flows must not accept binary image uploads, upload intents, storage keys, or
image-management commands.

When approved generated assets become available, the MVP may expose their
Cloudinary URLs through the existing optional image fields. The API and web
application only need to read and render those URLs safely; they do not own the
image-generation or upload workflow.

If no approved asset exists, the UI renders the existing accessible placeholder.
Image metadata must never be required for creating a muscle or exercise.

## Deferred post-MVP scope

After MVP, add Cloudinary-backed asset management for generated exercise and
muscle images:

- approved asset assignment and replacement
- admin-only upload/management workflows, if still required
- image validation and transformation policy
- alt text and presentation metadata
- safe removal and orphan cleanup
- CDN/cache behavior and operational monitoring

The post-MVP design must decide whether KinetiQ uploads to Cloudinary directly,
uses a server-mediated flow, or only stores URLs generated by an editorial
pipeline. Do not add `StorageService`, upload endpoints, or a media table before
that decision is approved.

## Data and API guidance

Keep image fields optional and transport-neutral. A Cloudinary URL is a
presentation reference, not an exercise or muscle domain identity. Do not
expose provider credentials, unsigned upload configuration, internal paths, or
generation metadata through public responses.

The MVP has no image-specific API endpoints. Future endpoints, if needed,
should be explicit admin operations rather than adding upload behavior to the
ordinary create/update commands:

```text
POST   /api/admin/exercises/:id/image
DELETE /api/admin/exercises/:id/image
POST   /api/admin/muscles/:id/image
DELETE /api/admin/muscles/:id/image
```

These are illustrative post-MVP routes and are not implemented.

## Frontend behavior

Catalog cards and detail pages use fixed image dimensions and an accessible
placeholder when `thumbnailUrl` is absent or unavailable. The MVP does not
render upload controls, progress indicators, crop tools, replace/remove
actions, or image-generation controls in muscle or exercise creation forms.

## Security and testing direction

For MVP, test that optional Cloudinary URLs render safely and that missing URLs
fall back to placeholders. Post-MVP tests must cover URL validation, admin
authorization, provider failures, cache behavior, alt text, replacement, and
cleanup. Never proxy arbitrary user-provided URLs or log provider credentials.

## Open decisions

Before implementing media management, approve the Cloudinary account/project
topology, upload ownership model, signed versus server-mediated uploads,
transformation policy, public asset domain, cache invalidation, and asset
deletion/retention behavior.
